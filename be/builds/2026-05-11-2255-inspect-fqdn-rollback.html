metal-desktop + nous (relay). What FQDN was, where it landed, and how to back it out so plain TOTP works again.

TL;DR

    • nous-desktop (UI) @ f8f192d -- 2026-04-07 "~s relay DNS default shipped"
    • nous (relay) @ facfbfc -- 2026-04-09 (parent of e1a376b "Board 6.1 register challenge + FQDN validation")

What FQDN added (the thing to remove)

The pre-FQDN flow: user enters username + TOTP code -> relay verifies TOTP against stored secret -> ok.

Register pre-FQDN: user picks username -> relay returns QR code -> user scans in Authenticator -> user enters TOTP -> verified.

Post-FQDN, register added a domain-ownership-proof step between username and QR:

  1. Pick username.
  2. Choose verification method: .well-known/metal-verify (place file at domain) OR Cloudflare API token (relay queries CF on your behalf).
  3. Relay returns a challenge token. You publish it to your domain.
  4. Click "Verify Domain". Relay does the lookup (DNS via -lresolv + HTTP fetch, or CF API).
  5. If verified -> relay returns QR -> scan + TOTP -> bound to your domain.

Same model added to reset-totp (re-verify domain to rotate TOTP secret) and auth lockdown (lock account after auth so registration can't be hijacked).

Two rollback strategies

Strategy A: Hard-reset to pre-FQDN commits

How: git checkout f8f192d in nous-desktop (for the UI); git checkout facfbfc in nous (for the relay). Cherry-pick desired post-FQDN improvements one-by-one if needed.

Cost: Re-rebrand work to match metal-desktop conventions. Lose every improvement since 2026-04-09 -- including catalog->prime rename, TLS 1.3 hardening, QR EC_M fixes, mktime TZ fixes, .well-known dual-method (which we want to remove but the FILE got other improvements too), 22-provider config refreshes, etc.

When to pick this: if FQDN's removal is too entangled to do surgically, or if you want to start from a known-clean baseline.

Strategy B: Surgical strip (recommended)

How: Keep current HEAD on both repos. Identify and remove only the FQDN-specific code paths:

  1. metal-desktop/wwwroot/index.html -- delete the domain-verification UI sections (auth-challenge-view, wkInstructions, cfInstructions, cfTokenInput).
  2. metal-desktop/wwwroot/desktop.js -- remove verifyDomainBtn handler, methodRadios toggle, the multi-step register flow. Register becomes: send relay_register {user} -> receive QR -> scan -> TOTP -> verify.
  3. metal-desktop/src/serve.c -- remove WS handlers for relay_verify_register, relay_verify_reset, relay_reset_totp. Pass relay_auth + relay_register straight through to relay.
  4. nous/comms/skill/relay/relay_server.c -- remove FQDN-validation gate on register, remove verify-register/reset/well-known route handlers, remove CF API client. Keep TOTP register (immediate QR) + login.
  5. nous-desktop CLAUDE.md docs -- update "FQDN identity / domain ownership" text to "TOTP only".

Cost: Careful manual editing. Estimate: ~3-5 pts on desktop side, ~5-8 pts on relay side. Need to test that TOTP register/login round-trip works after.

Benefit: keeps all post-FQDN improvements (catalog->prime, TLS, bug fixes). Smaller code surface (FQDN gone). Same TOTP UX as pre-FQDN.

The relay-binary problem (independent of rollback)

Even with FQDN removed, you still need a relay running for TOTP. Current state:

  • Public relay at relay.3-nous.net:8080 is dead (HTTP 000; DNS resolves to 35.236.92.148 but port 8080 doesn't respond).
  • No Windows build of relay_server. The existing build_linux.sh requires -lresolv (Linux DNS) and references WSL paths.
  • No production-relay Make target in nous/comms/Makefile -- only test binaries.

So before ANY desktop session works, the relay needs to be (a) built for Windows, (b) running locally on localhost:8081, (c) PSK matched with desktop's triples.key. That's a separate piece of work whose cost is independent of the FQDN rollback.

Recommended sequence

  1. Decide A vs B. Recommend B (surgical).
  2. ~p the rollback as a board. Sized items for desktop-side strip + relay-side strip + Windows relay build + smoke test. Estimate ~21 pts (one board).
  3. ~e and ~b through the board. Items in order: relay Windows build (unblocks everything), strip FQDN from relay, strip from desktop, smoke register + login round-trip on localhost.
  4. ~s on each repo separately (metal-desktop + nous). GitHub PRs would be ideal but you generally ship to main directly here.
