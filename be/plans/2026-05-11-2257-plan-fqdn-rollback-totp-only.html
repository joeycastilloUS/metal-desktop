Plan: Roll back FQDN, restore TOTP-only

Surgical strip of FQDN code across metal-desktop + nous/relay_server.c so plain TOTP register + login works again.

Plan -- Awaiting Approval

Intent

Joey wants to play with metal-desktop again. The current auth gate requires FQDN-identity (prove domain ownership via .well-known/metal-verify or Cloudflare API token) before he can register or log in. The pre-FQDN flow was simpler -- pick a username, get a QR, scan in Authenticator, enter TOTP. That worked. We're restoring that simpler flow.

Reference inspect: be/builds/2026-05-11-2255-inspect-fqdn-rollback.html.

Scope

In

  • Strip FQDN from nous/comms/skill/relay/relay_server.c -- remove verify-register, verify-reset, .well-known route handlers, CF API client, FQDN validation gate on register. Keep TOTP register (immediate QR) + TOTP login.
  • Strip FQDN from metal-desktop -- remove the multi-step register UI (domain verify view, methodRadios, CF token input, .well-known instructions). Register UI becomes: enter username -> click Register -> show QR -> enter TOTP -> verified.
  • Build relay for Windows -- writeups Makefile target for the relay server. Without FQDN, no -lresolv needed; the build becomes straightforward gcc with ws2_32 winhttp bcrypt.
  • Smoke test -- run relay locally, register a test user via the desktop UI, complete TOTP enrollment, log in, confirm cockpit unlocks.

Out

  • Hard-resetting to pre-FQDN commits (Strategy A from inspect). Losing the catalog->prime rename, TLS hardening, and bug fixes since FQDN landed is not worth it.
  • Re-enabling the public relay.3-nous.net:8080 -- dead, separate concern.
  • Deploying the relay anywhere besides localhost. This rollback gets us to "local single-machine usable"; cloud deploy is a future board.
  • Backporting any post-FQDN improvements that depend on the FQDN scaffolding (if any). The strip needs to be carefully written to keep TLS, prime rename, etc. intact.

Approach

  1. Strip relay first. The relay's FQDN handlers are the system-level gate. Removing them simplifies the dependency tree (no DNS lookups -> no -lresolv). Easier Windows build after.
  2. Add Windows Make target for the relay -- adapts build_linux.sh to gcc on MinGW with the right link flags. The relay was Linux-only because of -lresolv; without FQDN that goes away.
  3. Strip desktop UI. Remove the multi-step register screens. desktop.js shrinks. serve.c WS handlers reduce.
  4. Smoke locally. Start relay on localhost:8081 with a PSK, point desktop's desktop.conf at it, register a test user, complete TOTP, log in.

Phases

  1. Relay strip (nous/comms/skill/relay/relay_server.c) -- remove FQDN handlers, validation, CF/DNS code paths.
  2. Relay Windows build -- new Makefile target or build_win.bat.
  3. Desktop strip (wwwroot/desktop.js + wwwroot/index.html + src/serve.c) -- remove domain-verify UI, simplify register flow.
  4. Smoke -- end-to-end register + login on localhost.

Constraints

  • Two repos affected: joeycastilloUS/metal-desktop + kastil-systems/nous. Each ships its own commits.
  • PSK must match between desktop's desktop.conf (or compiled-in default) and the relay's expected key. triples.key file in metal-desktop's root.
  • TOTP secrets persist in the relay's state file (per-user). Existing users in the relay's store will keep working (their TOTP secret is still valid).
  • Keep TLS 1.3 hardening, catalog->prime rename, QR EC_M fix, mktime TZ fix. These landed AFTER FQDN; they stay.
  • Don't break the running metal-desktop server we launched earlier today. It's PID 1218 on neo, can be killed before smoke.
