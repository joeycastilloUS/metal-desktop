~i — metal DE vs. api.3-nous.net

Is the metal Desktop Edition cockpit using the nous.api multi-model gateway? Ground truth from files on disk plus live probes, driver (Opus) and navigator (Fable) run concurrent and reconciled per Kernel Rule 1.

Verdict

NO — metal DE does not use api.3-nous.net. Zero references anywhere in C:\metal-desktop — source, wwwroot, config, tests, or be/ records. It calls seven vendor APIs directly over HTTPS with keys resolved on the operator's box.

metal CE already does use it. C:\metal\src\ask\nous-ask.c:22 defaults to https://api.3-nous.net/v1/chat/completions. So this is a DE-only gap, and the two editions have diverged on model access.

DE's own architecture already says it is wrong. a-d-d/ARCHITECTURE.md:8 — "It is a consumer of nous.api, not the home of its logic." The code has not followed the spec. Under Rule 12 (flow up before down) that is drift, and the spec is the side that is already correct — no architecture change is needed to justify the cutover.

What It Is

api.3-nous.net is the nous.api multi-model gateway — one OpenAI-compatible front door that fronts every model vendor, so a consumer holds one token instead of seven vendor keys. Probed live from this box on 2026-07-26 (port 443, not a blocked high port, so no Rule 14 vantage caveat applies to these results):

Keys resolve locally through resolve_key() — a 4-layer chain user > env > builtin > NULL (src/nous_userkeys.c, src/nous_keys_builtin.h.example). Free-tier rows carry compiled-in NOUS_KEY_* builtins; paid rows read ANTHROPIC_API_KEY, OPENAI_API_KEY, etc. DE's own schematic states it plainly: "38 models (direct HTTPS)… No mesh hop" (be/designs/2026-06-13-0338-schematic-nous-api-mesh.html:86).

Used by auth / register / store / intelligence handlers at serve.c:718, 756, 867, 1000, 1120, 1232, 1329, 2032.

This is the correct wire plane per canon. It is not the thing that is wrong, and the cutover must not touch it.

Patterns Found

  1. Spec-ahead-of-code drift, and the spec is right. a-d-d/CLAUDE.md:42 — "These handlers carry the AI logic AND the WebSocket framing in one place. That is the thing to undo." The intended end state is already written: serve.c keeps HTTP + WS framing, and a thin route_ws_message calls nous.api. The work is subtraction, not invention.
  2. CE is the working precedent. nous-ask.c is C99 hitting the gateway over HTTPS with NOUS_API_URL / NOUS_API_TOKEN env overrides — the exact shape DE needs, already proven in the sibling edition. A C# jacket also exists for the bridge (NousGatewayClient.cs, metal be/board.md:314, CODE-COMPLETE).
  3. The gateway serves the Mission directly. /v1/models flags gemini / deepseek / mistral rows free:true. Routing DE through the gateway puts the free tier one config change away — Zero Cost Intelligence, not a rewrite.
  4. Two prior verdicts in this repo are now stale and should not be trusted by the next session. See below — both were called on evidence that no longer holds.

Stale prior verdicts — corrected

(a) "nous.api is spec-only, nothing deployed." — be/plans/2026-07-11-0918-inspect-nous-api.html, 15 days ago. False today. The gateway is deployed and serving /v1/models at HTTP 200. That inspect deliberately avoided curls from this box; the deployment landed after it was written.

(b) "relay.3-nous.net:8080 is dead (HTTP 000)." — be/builds/2026-05-11-2255-inspect-fqdn-rollback.html:46,119, echoed into the Board 6 shelve rationale. Not supported. A TCP connect to relay.3-nous.net:8080 from this box on 2026-07-26 returned OPEN. The original "HTTP 000" was a curl against a wire port — a protocol mismatch, which is exactly the Rule 14 failure mode. Open TCP is not proof of a healthy relay either; a same-plane wire handshake is still needed before anyone calls it up. But "dead" is retired as a finding, and Board 6's shelve rationale rests partly on it.

Splits — surfaced, not resolved silently

S1 — Relay liveness. Navigator: "relay.3-nous.net:8080 wire status NOT probed — unknown." Driver probed it: TCP OPEN. Not a contradiction — a gap the driver filled. Consequence is real: the "dead relay" premise under Board 6's shelve is retired.

S2 — Canon reading. Driver raised the wire-protocol rule as an open tension. Navigator resolved it with better evidence and a sharper cut: the wire rule governs talking to Purcius/the substrate; api.3-nous.net is a foreign-model gateway fronting vendor HTTPS, so model traffic over HTTPS is no conflict — and the 2026-07-10 design sanctions it explicitly. But: if anyone proposes the gateway as a substitute for the relay/prime for auth / store / loop, that would violate canon. Navigator's read is adopted.

S3 — Sanctioned consumer. Navigator flags that the 2026-07-10 design names the C# gcp-bridge jacket as the gateway's consumer, not a C99 client — a Language Boundary question for DE. Driver's counter-evidence: CE's nous-ask.c is already C99 straight to the gateway. Reading forward: the C# jacket rule covers third-party manufacturer APIs; the gateway is ours, and it is the thing that removes third-party HTTPS from our C99. Unresolved — operator's call (open question OQ2).

S4 — Provider count. Navigator cites "38 models" from the schematic; driver counted 22 live rows in g_defaults[]. Doc drift, minor, but the schematic overstates current reality.

Open Questions

  1. OQ1 — Token. Hard blocker. NOUS_API_TOKEN is unset in both User and Machine environments on this box. POST /v1/chat/completions returns 401 without it. Nothing downstream — not a build, not a test, not a production verification under Rule 10 — can complete until the operator pastes one (Rule 5: he pastes, Be installs). CE's own nous-ask cannot run here today either.
  2. OQ2 — C99 direct, or through a jacket? Does DE call the gateway straight from C99 (CE's precedent) or must it route via the C# NousGatewayClient? This changes the shape of the whole cutover.
  3. OQ3 — Feature parity unproven. Whether the OpenAI-compat shape carries everything DE's 22 rows need — streaming, Anthropic-specific fields, per-model cost accounting for the cost receipt — could not be tested without the token.
  4. OQ4 — Model Garden enablement. Which of DE's 22 model ids exist and are ENABLED on the gateway. /v1/models lists 25+ but the id sets do not map one-to-one (e.g. DE carries o3, o4-mini, grok*, perplexity*; the gateway list surfaces vertex rows DE has never had).
  5. OQ5 — Does the free tier survive? DE ships compiled-in free keys today. The gateway flags rows free:true behind one token. Which path is cheaper and more honest to the Mission is a design decision, not an implementation detail.
