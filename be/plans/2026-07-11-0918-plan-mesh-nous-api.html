Plan — nous.api Mesh Front Door

Route ALL model calls through one mesh front door — four verbs (ask / judge / summarize / reconsider), BYOK in the mesh, no key on the operator's box, primes near provider datacenters.

PLAN — AWAITING APPROVAL
Relationship. This plan realizes the tagged architecture decision (all model calls through nous.api) and is the model-access layer the metal.de Finish plan deferred to the mesh horizon (be/plans/2026-07-11-0820-plan-metal-de-finish.html). Grounded in the same-timestamp inspect: be/plans/2026-07-11-0918-inspect-nous-api.html — verdict: mesh nous.api is spec-only (zero implementation C, nothing deployed serving the verbs); the living donor is metal-de's serve.c (5,568 lines, task/judge/summarize working today, keys on-box). This is an EXTRACTION job, not an invention job — the extraction map is already written in fanout's CLAUDE.md ("fanout is handle_task minus the WebSocket I/O"). Estimate: ~2–3 weeks, 5 boards.

Intent

Stand up nous.api as the mesh's single model-access front door: extract the proven 38-provider fan-out engine out of metal-de's cockpit into standalone nous C skills, port judge + summarize, build the missing reconsider, wire the four verbs into api_dispatch() on the relay/prime path, and move key custody off the operator's box into the prime-side sealed vault with BYOK carried on the wire. When this lands, metal-de (and every future consumer — metal.ce tildes, Argus, anything on Purcius) makes model calls by sending a WireTriple to the mesh; the mesh resolves keys, fans out from primes near the providers, and returns triples. The operator's machine holds zero provider keys — that is the whole point.

Scope

In

  • Extraction of the provider table (38 rows, 5 wire formats) + thread-per-provider parallel fan-out from C:\tools\metal-de\src\serve.c into standalone nous C skills (providers, fanout) — the spec headers in C:\a-d-d\nous made real.
  • Ports of handle_judge and handle_summarize into judge.c / summarize.c; a small ~d + first implementation of reconsider (a TODO today, implemented nowhere).
  • api.c — the thin verb router (api_dispatch()) carrying NTRP triples relay → prime; deployment of nous.api onto a live prime.
  • BYOK on the wire: KeyOverride on FanoutOpts, precedence per-request override → vault → store → env; the prime-side sealed key vault; blank override = mesh-internal key.
  • Cockpit cutover: metal-de's local fan-out swapped for a relay_request to nous.api, with the local path retained as the offline bridge.

Out

  • The C# blind-REST edge on Cloud Run — the cockpit's existing authenticated relay_client.c wire path carries the verbs for v1; the REST jacket is deferred until an external (non-wire-speaking) consumer needs it.
  • New provider-adjacent prime nodes — v1 deploys to the existing 4 primes; "primes near provider DCs" is a deploy-topology goal tracked as follow-on placement work, not a gate on this plan.
  • Removing metal-de's local fan-out — it stays, demoted to offline bridge (constraint 4).
  • New verbs beyond the four; streaming (fanout_ask_stream) beyond what the cutover needs; billing/metering of BYOK usage.
  • Refreshing the old C:\nous\user\interface\desktop\serve.c generation — extraction sources from the living metal-de engine only; spec line-refs get corrected as touched.

Approach

  1. Extract, don't invent. The donor code runs in production today. provider_thread is the worker, handle_task is the driver — fanout is handle_task minus the WebSocket I/O. Lift the engine, leave the cockpit.
  2. Spec is already written — honor it, refresh it. Headers (api.h, fanout.h, providers.h) and the BYOK design (KeyOverride, 2026-06-19) exist in C:\a-d-d\nous. Architecture → tests → code (Rule 11): where the living engine has drifted past the spec (5 wire formats vs 3, line refs), flow the correction up to a-d-d first — as proposals, per Rule 10.
  3. Skills stand alone before they stand on the mesh. N1/N2 build and test the skills as pure C off-mesh (deterministic harness, canned provider responses); N3 is where the wire enters. Never debug extraction and transport in the same board.
  4. Key custody flips exactly once. Keys move box → vault in N4 as a single auditable change with the precedence chain proven by test; until then skills run on env keys in the harness only.
  5. Cutover with a lifeboat. N5 swaps metal-de's phase-3 fan-out for a mesh call behind a reachability check: mesh up → wire; mesh down → local offline bridge. No flag-day.
  6. Verify from the right vantage (Rule 13): mesh state gets a same-plane re-check (SSH a prime, peer curl over wire-TLS) before N3 deploys — MESH_STATUS.md is 42 days old. No conclusions from home-router curls.
  7. Plans are wrong by default. Reconsider has no donor and no prompt design; payload sizing over the 0xCA envelope is unmeasured. Unknowns and revisit triggers below are first-class.

Constraints the checklist

  1. Wire protocol only into the mesh. The four verbs travel as NTRP WireTriples over the relay/prime path (0xCA AES-256-GCM, wire over TLS) — never HTTP/REST/SDK into the substrate. The C# REST jacket, if ever built, sits outside as a blind edge and is out of scope here.
  2. C99 for everything we own. providers/fanout/judge/summarize/reconsider/api are pure C99 nous skills; C# exists only as foreign-API jackets, none needed in this plan.
  3. Keys never on the operator's box — the whole point. Custody is mesh-side (sealed vault on the prime); BYOK rides the wire per-request, RAM-only, never logged; blank = mesh-internal key. Post-cutover, no resolvable provider key on the operator machine outside the offline bridge.
  4. metal-de's local fan-out stays as the offline bridge. Demoted, not deleted — mesh unreachable means the cockpit still answers. The bridge is the one sanctioned residence of local keys.
  5. Primes near provider datacenters is a deploy-topology goal, not a v1 gate. v1 ships on the existing 4 primes; placement work follows with latency evidence from N3/N5.
  6. Architecture first (Rules 10/11). a-d-d/nous specs are read before each board; drift (wire-format count, line refs, vault node-class) flows up as proposals before code lands. Claude never writes a-d-d without approval.
  7. Done = production, externally verified (Rule 9). N3–N5 exits are proven from a machine other than this dev box, from the same plane as the real client (Rule 13).
  8. Plan shape honored + this banner stays until approved.

Unknowns named explicitly

  • Prime placement / latency — whether existing generic GCP zones give acceptable cockpit-to-answer latency once fan-out moves mesh-side, and what "near provider DCs" costs to actually do. Measure at N3/N5.
  • Per-provider vault provisioning — where the sealed vault physically lives (which node class — one prime? all primes?), how 38 providers' keys get provisioned/rotated into it, and who holds the seal. Nothing on disk answers this; settle before N4 starts.
  • Whether reconsider needs new judge state — "top-3 winners re-examine" may require judge to expose ranked state it currently buries in g_last_results; the N2 ~d decides if judge's port grows a state contract.
  • Mesh auth for the ask verb — the cockpit's PSK + cockpit-key relay auth exists, but whether it is sufficient authorization for model-spending verbs (and how BYOK requests bind to an operator identity) is unresolved.
  • 0xCA envelope sizing — whether relay_intelligence()'s triple round-trip carries 38 × MAX_RESPONSE fan-out payloads or the envelope needs chunking. Measure in N3.
  • Mesh liveness — MESH_STATUS.md is 42 days old; the same-plane re-check before N3 may surface hung primes/relays (Rule 13's exact lesson) and add restart/ops work.

When To Revisit the v2 triggers

  • N1 extraction fights the donor — if fanout can't separate from the WebSocket layer in roughly the promised lift (globals, socket writes tangled into provider_thread), the "extraction not invention" premise is wrong: stop, re-~d the skill boundaries.
  • Envelope can't carry the payload — if N3 shows 0xCA needs chunking/streaming, N3 re-opens with a transport sub-board before N4 proceeds.
  • Vault provisioning has no owner-approved home by N3's end — N4 stops; key custody is not improvised.
  • Latency makes the cockpit worse — if mesh round-trip meaningfully degrades the operator experience vs local fan-out, the placement goal (constraint 5) promotes from follow-on to plan v2's first board.
  • Auth gap is structural — if PSK + cockpit key can't bind spend to operator identity, pull the Operator-Identity Auth canon in before cutover; N5 waits.
  • Any a-d-d drift stop (Rule 11) twice in one board = plan v2 before the next board.
